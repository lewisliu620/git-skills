# 多公众号档案机制（wechat-account-profiles）

> 目标：让 lewis-topic-scout 支持**多个公众号**，每个公众号有独立的选题口径、写法要求、引流与署名规则；触发时按用户指定的公众号加载对应档案，动态可增删、可切换，不写死在 SKILL.md 正文。

## 1. 档案配置文件位置

- 档案数据统一放在 `assets/wechat-accounts.json`（与 SKILL.md 同目录下）。
- 档案结构说明见本文件第 3 节；`assets/wechat-accounts.json` 只存数据，不存规则。
- 新增 / 修改公众号时，只改 `assets/wechat-accounts.json`，不修改 SKILL.md 正文。

## 2. 触发时如何选择档案

每次出选题前，先确认本次为哪个公众号出题：

1. 用户明确说公众号名（如"给玖玖AI科技出选题"、"玖玖AI科技这周写什么"）→ 用该公众号档案。
2. 用户没说，但有上下文（当前会话正在维护的公众号、多维表里最近记录归属）→ 沿用该公众号档案。
3. 都没有 → 用 `assets/wechat-accounts.json` 里 `default` 标记的公众号档案，并在输出开头注明"本次按默认公众号 XX 出题"。
4. 用户指定的公众号不在档案里 → 提示用户先在 `assets/wechat-accounts.json` 新增档案（给出新增模板），本次按默认档案先行。

### 字段说明

| 字段 | 必填 | 说明 |
|---|---|---|
| `default` | 是 | 默认公众号 id；触发时未指定公众号用此项 |
| `accounts[].id` | 是 | 英文/数字 id，唯一，用于内部识别 |
| `accounts[].name` | 是 | 公众号对外名称（如 玖玖AI科技） |
| `accounts[].author` | 是 | 署名，写入文章作者信息 |
| `accounts[].subject` | 是 | 账号内容主题 |
| `accounts[].audience_type` | 否 | 客户类型：B端（企业客户）/ C端（个人用户）/ 混合；决定严谨性基调与语气 |
| `accounts[].target_audience` | 是 | 目标读者（与多维表「目标读者」选项对齐） |
| `accounts[].tone` | 是 | 语气要求；B端账号按"严谨专业"基调写 |
| `accounts[].rigor_rules` | 否 | B端严谨性硬规则（每条一个字符串）：可追溯、不夸大、术语准确、方法论有出处、结构化论证、讲成本风险、敏感合规；B端账号必填，C端账号可按需精简 |
| `accounts[].writing_rules` | 是 | 内容硬规矩（每条一个字符串） |
| `accounts[].readers_hook` | 否 | 读者钩子/吸引力方向 |
| `accounts[].reply_keyword` | 是 | 统一引流关键词 |
| `accounts[].lead_magnet` | 否 | 默认引流资料名 |
| `accounts[].publish_plan` | 否 | 发布与首发策略 |
| `accounts[].table_field` | 是 | 入表时写入「公众号」字段的选项值（须与该字段已有选项一致） |

## 4. 档案如何影响选题与入表

### 4.1 选题阶段（Step 1-3）

- 建热点池时，按档案 `subject` 过滤候选，只保留与本公众号主题相关的方向。
- 打钩子强度时，档案 `target_audience` 决定"传播点"判断（读者看完愿不愿意转给同行 / 老板）。
- 硬规矩（`writing_rules`）在选题阶段预判：选题不得触碰档案红线（如价格、微信号、硬引流）。
- **B端账号额外预判**：按 `rigor_rules` 检查选题是否可能涉及夸大承诺、不可追溯的数据、无出处的理论；有风险的角度直接降级或淘汰，或在选题时就设计好"口径标注/来源说明"的写法。

### 4.2 输出清单（Step 4）

- 每个选题输出时，额外标注：`公众号：<档案 name>`。
- 引流资料默认取档案 `lead_magnet`；单篇可微调，但关键词统一用档案 `reply_keyword`。
- **B端账号**：标题可以有钩子，但不得夸大承诺；每个选题注明"写作时需标注的来源/口径"。

### 4.3 自动入表（Step 6）

- 「公众号」字段写入 `table_field` 值（如"玖玖AI科技"）。
- 若该值不在「公众号」字段选项里，先按档案值更新字段选项（`+field-update`），再写入记录。
- 「目标读者」写入值必须与多维表「目标读者」字段选项一致；新读者类型先扩展选项再写入。

### 4.4 自动写作（Step 8 → content-pipeline）

- 把档案的 `author`、`reply_keyword`、`writing_rules`、`tone`、`rigor_rules` 一并传给 content-pipeline，作为该篇的写作与署名约束。
- 推送公众号草稿箱时，推送对象以档案 `name` 为准。

## 4.5 B端严谨性检查清单（成稿前必须过一遍）

适用于 `audience_type` 含"B端"的公众号（当前默认档案玖玖AI科技必须执行）。成稿前逐条检查：

1. **数字可溯**：文中的每个数字/比例/案例，要么有明确来源（来源名 + 可检索出处），要么标注"示例/假设/个人估算"；找不到来源的数字直接删掉或改写为定性描述
2. **无夸大词**：通篇不得出现"颠覆、神器、立竿见影、疯狂、暴涨、一夜暴富"等营销化词；效果用"可能/视情况/建议先试点验证"等克制表达
3. **术语先定义**：MCR/LTC/GTM/赢率/健康分等概念首次出现有准确定义，不堆术语
4. **理论有出处**：引用华为等大厂做法时说明来源（如官方资料/公开报道/行业研究），并区分"大厂实践"与"中小企业简化落地"，不把个人理解冒充官方口径
5. **讲清成本与风险**：讲收益的同时给出成本（时间/人力/工具投入）与风险（数据治理、采纳率、组织阻力），并给出"什么情况适用/不适用"
6. **结构完整**：按"问题→原因→方法→动作"组织，结论与前面论证一致，不跳步
7. **合规敏感**：不泄露具体客户/企业数据，不教违规操作（如绕过系统、数据造假、刷单）
8. **署名与引流**：作者按档案 `author`；正文无微信号/价格/硬引流，引流只在文末"回复关键词领资料"
9. **排版配色合规**：正文为深灰 #333333（全文无纯黑 #000000）；重点金句用品牌蓝 #4A90E2 加粗高亮且只标短句/关键词（无整段高亮）；注释/来源用浅灰 #888888；全文文字配色 ≤3 种；高亮占比 ≤10%；正文 15-16px、行距 1.75、左对齐无首行缩进、每段 ≤3-5 行

> 检查不通过 → 回到写作阶段修改原稿，不得带着违规项交付。

## 5. 新增公众号档案（动态设置）

用户要新增公众号时：

1. 在 `assets/wechat-accounts.json` 的 `accounts` 数组追加一个对象，字段按第 3 节模板；B端账号必须填 `audience_type` 与 `rigor_rules`。
2. 如需切换默认公众号，改顶层 `default`。
3. 检查多维表「公众号」字段是否含该公众号选项；不含则 `+field-create` / `+field-update` 加选项。
4. 检查多维表「目标读者」字段是否含该公众号的读者类型；不含则加选项。
5. 完成后告知用户已生效；SKILL.md 正文不用改。

## 6. 与「公众号内容硬规矩」章节的关系

- SKILL.md 正文「公众号内容硬规矩」章节是**默认/兜底**规则，适用于档案未覆盖的场景；
- 档案 `writing_rules` 优先级更高：同一事项档案有明规则时按档案执行，档案未写时回落到 SKILL.md 兜底规则。

## 7. 档案在"选题评审与归档"中的用法（评审锚点）

评审多维表里已存在的选题（评审/批量修改/标记已放弃）时，档案同样生效，规则见 SKILL.md「选题库评审与归档铁律」：

- **按「公众号」字段找档案**：每条选题以「公众号」字段值为键，加载对应档案（`subject` 主题过滤 + `rigor_rules` 严谨性 + `writing_rules` 硬规矩）评审；字段值为空时**不得加载任何档案**，按中立待写池处理，不用任何公众号标准评判或标「已放弃」。
- **B端账号评审**：玖玖AI科技等 `audience_type` 含 B 端的账号，评审时逐条对照该档案 `rigor_rules`（数字可溯、无夸大、术语先定义、理论有出处、讲成本风险、合规敏感），处置类别限「保留 / 合并去重 / 修订 / 归档」，归档须在备注写明"归属公众号 + 理由 + 日期"。
- **批量处置前先分组**：用 `+record-list --format json` 全量拉取，按「公众号」字段逐条核对分组，再逐组评审；禁止跨账号一刀切（如用 A 号标准批量标 B 号或无归属选题）。
- **档案不含该公众号**（如无归属选题被用户指定给某个未建档公众号）→ 先按第 5 节新增档案，再按新档案评审；未建档前保持「待写」不动。
