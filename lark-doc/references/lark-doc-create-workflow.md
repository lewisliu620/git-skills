# docs +create（创建飞书云文档）

本文内容较长，如果一次不能读取完成需要分多次读取，直到读取到“===全文完===”为止。

本工作流统一处理飞书云文档创建：

- **从零创作 / 基于原文改写后另建新稿**：进入[“创作与改写新稿”](#创作与改写新稿)，按以下核心顺序依次完成：**理解需求与用户过往写作风格 → 收集素材 → 内容与排版共同规划 → 提交 Decision 并初始化 → 生成 XML → Draft Profile Check → 创建并回读 → 交付。** 基于原文改写时，在本文件 Step 1 中读取原文、明确保留要求并获取历史样文；已有原文不能代替 `writing-references` 调用。
- **在原文档上改写**：走 [`+update`](lark-doc-update.md)，同样先读取历史样文并模拟用户风格，只修改用户要求的范围。
- **创建空文档 / 原样导入完整内容**：直接使用 [Shortcut](#shortcut)；需要改写原文后再创建时，按上面的“创作与改写新稿”流程执行。

---

## 创作与改写新稿

**CRITICAL：从零创作或基于原文改写后另建新稿时，优先找到主题、内容和体裁相近的过往文档；完整阅读，研判表达与文档结构习惯、筛选原文 few-shots。生成时持续参照作者的实际写法；用户本次明确要求优先，不可跳过所选路径中的必经步骤。**

### 基本约束

- **约束栈**：事实 > 用户本次明确要求（指定的模板、内容结构、呈现方式、附件/指定链接）> 用户过往文档的写作与排版风格 > 本 skill 的通用写作指导建议；后项不得放宽前项，格式与组件不得反向改变内容判断。

- **默认不打断**：需求不完全明确时按合理默认推进，不为小问题反复发问；只有确实无法推进的硬阻塞才停下来，向用户说明并提问。
- **写作风格**：尽量模仿用户的写作风格（除非用户明确告知不要这么做），通过读取用户过往的写作文档（除非用户明确告知），依据原文 few-shots 忠实复现其语言和组织习惯，包括稳定的非标准表达与习惯性语病，不以通用写作规范擅自修正。不允许因为任务简单、时间紧张或者已搜索到部分文档而跳过读取用户过往写作文档的步骤。若没有过往写作文档参考，则依据 skill 中的体裁指导写作。
- **禁止编造事实性内容**：禁止编造数据、引用、客户案例、实验结果或来源。

### Step 1 · 理解任务需求

先确定：**目的、受众、篇幅、写作类型、输入类型**。

- **理解用户任务**：确定核心写作类型，确定写作目的、作者或主体、主要读者，以及用户明确要求和排除项，据此确定需要从附件或外部来源补充哪些信息。
- **对于基于原文改写的任务**：先读取待改写范围及必要上下文，整篇改写时先完整阅读原文，明确需要保留的事实、观点、限定条件和资源。原文可能来自他人、模板或 AI，不能仅凭用户提供了原文就认定其中的写法是用户风格，仍须执行下述 step 2 中的 `writing-references` 步骤。
- **篇幅**：用户指定则以用户为准；若无指定，则参考 step 2 中读取的用户过往文档风格。

### Step 2 ·  确定写作风格

#### Step 2.1 · 读取用户过往写作文档

- **读取用户过往写作文档**：**执行 `../scripts/personal_style.py` 文件获取用户过往写作文档`writing-references`**，**注意禁止使用如"2>&1" "head" 等指令，脚本本身已经做过类似操作，继续使用该类指令会造成重要内容丢失**，直接执行即可。
注意，必须使用这个接口读取文档，而不能使用搜索结果中的文档、前轮中的文档和上下文中的文档替代这个接口返回的结果。
如果这个接口成功返回内容，执行 Step 2.2 理解用户风格，并跳过 Step 2.3 直接执行 Step 3；如果接口返回失败或返回为空，跳过 Step 2.2 直接执行 Step 2.3。

#### Step 2.2 · 根据用户过往写作文档，理解用户写作风格并记录

- **主样文来源限定：除用户本次明确指定模板外，主样文必须是`../scripts/personal_style.py`召回的文档，从`writing-references` 返回且已完整读取的历史文档中选定。禁止将统一任务中企业搜索到的文档直接作为个性化写作样文，即便是体裁一致的文档，找到的文档只要未被该接口召回，也只能作为事实来源，不得用作个性化写作的主样文。**
- **优先匹配主题、内容与体裁**：先从过往写作文档中寻找与本次主题、讨论对象及具体内容最相似的文档和片段，在内容相关的候选中优先参考体裁相近的文档，再结合写作目的、受众和段落用途选择。不能仅因文档更新、更符合某种格式或标题相近，就越过正文内容更相关的参考；体裁用于匹配真实历史文档，不用于套用通用写作模板。
- **完整读取样文正文与结构属性**：主样文必须按 +fetch 使用 lark-cli docs +fetch --doc "<document_id>" --detail full 获取整篇文档并完整阅读，禁止使用 `--detail simple` 获取。`writing-references` 返回的其他相关文档若已知为节选、标明截断或有正文被截断的迹象，同样须按 [`+fetch`](lark-doc-fetch.md) 使用 `lark-cli docs +fetch --doc "<document_id>" --detail full` 获取整篇文档并完整阅读。优先使用 `document_id`；仅有链接时使用不带选区或块锚点的文档根 URL，不传局部 `--scope` 或深度限制。不能只读命中片段或局部章节，也不能以节选已足够判断风格为由跳过；此处全文要求优先于参考文件中按需补读、最小范围读取的通用建议。返回内容过长时可落盘分段读取，直至覆盖完整正文，再筛选 few-shots；已有完整正文及所需结构属性时不重复获取，获取失败时如实说明，不能把节选当成已读全文。
- **筛选 few-shots**：在已读取的相关正文中选定最相近的主参照，以其中与本次任务对应的完整结构作为模板；文档包含多期记录时，选定其中一期的完整记录，不混拼各期结构。保留模板的标题层级、章节顺序及各部分的排版，再提取与本次内容相似、且能体现其整体顺序和对应部分写法的原文片段，保留理解开头、正文及收尾所需的上下文。保留连续段落或相邻要点，避免只摘孤立金句。其他相关原文可用于印证习惯或补充主参照缺少的段落用途，不把不同场景的写法混成折中文风，也不把全部历史文档直接作为示例。
- **保留原文与结构**：片段应包含足以理解写法的上下文，保留原有用词、断句、标点、段落边界，以及标题层级、列表类型与父子归属、各类 block 的顺序和嵌套，不先摘要、改写或润色。选取子项或局部 block 时，连同理解其用途所需的上级标题、父项和相邻内容一起保留，不能把深层子项摘成平铺要点，也不能将不同 block 一律提取成纯文本段落。记录来源文档、片段位置与原文上下文；已取得完整正文但缺少结构信息时，按接口说明用 `+fetch --detail full` 补读所需结构，不人为截断标题或列表深度。
- **仔细研判习惯**：结合所选原文的上下文，理解每级标题如何划分内容、段落与列表分支如何展开、各种 block 在何处承载什么内容，以及作者对哪些内容展开、哪些内容简述，客观识别作者的特点及其原有使用条件；不能只看文字措辞而忽略文档结构和内容轻重。需要关注和认真研读的写作风格包括但不限于以下维度：
  - **句法与节奏**：长句、短句、短语如何搭配，句内并列或从句怎样展开，是否省略主语，在哪里用逗号、分号、括号或换行停顿。样文用长句承载连续论述时，不为“简洁”拆成碎句；样文用短句或省略句时，不补成完整长句；长短交替时，不统一成一种句长。
  - **段落与组织**：连续成段还是一句一段，先结果还是先过程，背景、理由、例子与结论放在哪里，开头如何进入主题，段间如何衔接，以及收尾和详略的习惯。
  - **内容重心与详略**：认真读出用户在相近内容中重点展开什么、展开到何种具体程度，哪些信息只给结论、状态或简短交代，以及细节如何支撑作者关心的问题。本次对应内容沿用这种轻重与展开方式，不因材料多就都展开，也不把所有部分统一压短或平均分配篇幅。判断需结合内容本身和上下文，不能把节选截断、材料缺失或一次偶然省略误当成用户偏好。
  - **列表与层级**：是否使用列表、什么内容写成列表，有序或无序及其混用方式，父项与子项的关系、嵌套深度、同级项排列，以及每项是短语、整句还是多段说明。用户习惯多层列表时，保留相应分支和归属，不默认限制为一两层、不拉平；用户习惯连续段落时，不因内容可分点就列表化。
  - **多级标题与强调**：结合原文标题属性，逐级确认标题的实际 heading 级别、哪些标题并列或从属，以及每个标题下写哪些内容。看清各级标题有没有编号，以及是通过 `seq="auto"` 设置原生自动编号，还是直接将序号写在标题文字中。同时观察标题怎么写，以及加粗、空行和引导语的用法；标题层级与列表层级分开判断。
  - **block 使用与组合**：原生段落、表格、引用、callout、分栏、图片、画板、HTML 等何时出现，分别放在哪里、与哪些内容相邻或嵌套，以及如何表达强调、说明或对比。按样文实际采用的类型、组织方式和视觉习惯承载本次内容，不因工具可用就增加组件，也不因内容相近就擅自把一种 block 换成另一种。
  - **措辞与语气**：人称、口语或书面表达、术语与简称、中英混用、数字和单位写法，以及判断的直接程度、保留措辞和常用连接词；沿用表达习惯时，不改变本次事实的确定性或语义。
  - **个人化与非标准用法**：原文中反复出现的口头表达、重复、搭配或语序偏好、成分省略和习惯性语病，在本次没有明确要求纠错、润色或规范表达时，作为作者习惯保留，不仅因通用建议就补全或改写。只继承原文有依据的习惯，不凭空制造语病，也不把偶发笔误扩大成固定风格。
- **记录用户写作风格**：新建  `writing-style.md` 文件：将用户写作特点、典型片段 few-shots 和你预期的常规写作不一样的用法，详细记录在  `writing-style.md` 文件中，以便后续写作时参考。
- **常见风格偏差checklist**：如果用户不使用高亮块，或者用户不使用“一”、“二”等文字编号，或者用户不在文末不会罗列参考文档，那么要**把这些习惯也明确记录下来，而不要使用模型默认的习惯**。
- **再次确认**：写作风格仅参考了personal_style.py接口中获取的文档片段，而没有被上下文或搜索材料中的材料所干扰。
- **参考不足时**：没有可用过往文档或读取失败时，如实说明，依据用户本次要求、已提供材料与适用的通用指导完成任务；不得将错误当作成功空结果，也不得声称已了解或模仿未读取的用户风格。有节选但全文获取失败时明确证据限制，不把节选标成全文。

### Step 3 · 理解材料，形成具体内容与全文主线

按用户任务收集所需事实、数据与已有素材，结合主参照的写作风格确定内容与呈现方式。

#### Step 3.1 收集素材

- **阅读用户附件与链接（重要性与权威性都最高）**：用户上传/提供的一切材料（附件、超链接）都是本次任务的第一手事实来源，优先级高于联网搜索和你的先验知识。用户附件里有很多关键信息藏在图/表/公式里，只跑 `paragraphs` / `pdftotext` 会丢掉它们；如果之前读取附件时只获得了文本信息或没有读取附件，那你必须再一次解析附件内容获得更多相关信息，docx 必须读取 `doc.tables`、`doc.inline_shapes` 和 OOXML 包内的 `word/media/`，pdf 必须读取 `fitz.get_images`、`fitz.find_tables` 或使用 `page.get_pixmap` 获得页面截图。用户提供的外部链接也必须完整解析：优先使用可用的语义读取或浏览器能力获取页面正文、标题、作者和发布日期等元信息；确需本地抓取时，使用 Python 的跨平台 HTTP/HTML 库，动态页面则使用浏览器渲染后再解析。链接内嵌的图片、表格、代码块等富媒体内容也要一并读取。附件和链接中的图片/表格插入 doc 时，必须保留原图表的所有信息，**绝对不允许做裁剪，但是可以缩放大小来适配 doc 的排版布局**；与其它来源冲突时以用户提供的附件和链接为准。
- **区分每份材料的用途**：本次事实依据、写法参考，或兼具两者。事实部分用于本次内容，样文中的旧事实不因作为参考而自动采用。
- **联网搜索**：补齐本次任务所需的真实数据、事实、案例；不得编造，缺失就标注占位/假设/待补，并标注来源。不因搜索到更多素材而自动扩写背景、案例或解释。
- **搜图工具**：真实实体（人物、产品、logo、地标等）对应的图片必须用搜图工具获取。搜图时每次少搜一些（工具默认返回 6 张，可把数量设为 4 张），避免一次拉取过多。
- **生成图片**：在任务明确需要插画、视觉概念或示意素材时使用，不作为缺失真实照片的替代。生成后检查是否贴合文档主题，图中文字与细节是否正确。

#### Step 3.2 多材料整合

- **最重要的素材原则** 用户提供的附件和链接>=1时，需要严格遵循此规则：多附件任务不是逐份概括材料，而是先理解材料之间的关系，再组织成一个完整、可核验的交付物。**如果之前读取附件的时候将内容压缩为了摘要，丢失了细节，则需要使用细节时务必重读**，并且在思考过程中记录每个附件的角色，**先弄清材料之间是什么关系、每份材料在最终文档中负责什么**。
- 每份材料都应先找出它独有、不可由其他材料替代的信息，再判断哪些是本次任务必需的；完整阅读不等于全部写入，材料数量和长度不直接决定成稿篇幅。

#### Step 3.3 确定具体内容与组织方式

**确定具体内容**。写清主要回答、对象、关系、数据及依据，保留必要的条件和明细。

若 Step 2.1 中获取到了用户过往文档，则参考用户写作风格进行写作，除非用户禁止；否则按照 Step 2.3 中的体裁写作指南进行组织。当按体裁写作指南组织内容时，简单任务可参考文本排版组件中的文字 1500 字以内，完整方案建议 3000-5000字，必要信息较多时允许适当展开，除非用户明确指定字数。

### Step 4 · 依据内容规划排版与可视化

**重要说明：**

在理解 Step 2 中写作风格的基础上，规划排版与可视化。可视化必须服务于写作风格，本步骤中提供了一些可视化建议，但若用户过往写作风格中已经体现了明显的可视化特征，则不允许与用户风格冲突，例如，如果用户完全不是用某项可视化效果，那么在后续写作中也不应该使用。

进入 XML 制作前，先读[XML 制作指导](lark-doc-xml.md)，如果需要制作html-block，需要同时读取 [HTML block 视觉与文字指导](lark-doc-html-block.md)。

#### 表达载体与图型建议

| 需要读者看懂或完成什么 | 主表达载体 |
| --- | --- |
| 一个判断及其理由、依据或条件 | 段落；一段完成一个意思。 |
| 并列的判断、理由、材料或动作 | 无序列表；每点承载一项信息。 |
| 简单、无分支的顺序操作 | 有序列表；每步写清动作与结果。 |
| 同一组维度上的对象比较，或需要查阅、修改的明细 | `table`，包括复杂文字矩阵；先定比较轴，再安排格内标题、分点与条件。 |
| 需要读者继续编辑节点、连接或结构的关系图 | 优先考虑HTML block 或画板，让读者能够继续调整节点、连接与分组。 |
| 需要定制布局、关系标注、组合视图或局部交互的关系与数据特征 | HTML block；可以静态呈现，也可用交互补充信息。数据图表类型鼓励交互。|
| 真实界面、现场、产品、原始图表或需要辨认的视觉细节 | `img`；保留必要上下文与来源，不能用生成图冒充真实资料。 |
| 少量并列内容需要同时阅读 | `grid`；各栏内容简短，宽度和阅读顺序清楚，不代替有比较轴的表格。 |
| 需要持续计算、筛选的数据 | 使用可交互的HTML block，用户可以进行数据筛选；文档只保留当前判断所需的摘要、图或引用。 |



图型按内容意图选择，仍不可与用户写作风格冲突。
- **主动识别关系与数据特征**。从文字、表格和已有素材中寻找联系、差异、趋势、构成、分布、集中度、目标偏差及异常等。即使预算、成本等数据已经在表里，也要判断是否需要用图帮助看出分配重点。
- **图形准确表达信息**。编号表达顺序，位置表达并行或归属，连接表达交接、依赖和反馈。并排卡片本身不等于协同；节点、标签和正文保持同名同口径。
- **数量表达有依据**。区分实际数据、规划目标和方案假设。桑基、定量漏斗使用可核对的数量及一致口径；没有数量时画流向或阶段关系，不以宽窄暗示虚构比例。
- **尺度支持准确比较**。用长度、位置、面积或颜色编码数量时，尺度须对应数据；条形图数量轴从零起，同组比较采用一致尺度，不能混用不同单位。步骤编号不当作数量编码。
- **重点就近标注**。先确定主要判断，再安排排序、基准和标注。关键差距、拐点与异常标在对应位置；单位、时间范围、假设和必要来源就近说明。
- **互补而不重复**。图帮助看关系或模式，表帮助查明细，文字补依据和条件；不把整张原表搬进 HTML，不给每张表配图，不按章节凑图数。
- **图形符号**。图表和 HTML block 的符号习惯参照样文；没有本次要求或样文依据时，不额外加入 emoji。

| 可用图表类型         | 内容意图与表达方法                                       |
| -------------- | ----------------------------------------------- |
| 时间轴（Timeline）  | 阶段演进、路线图、里程碑、事件序列。                              |
| 桑基图（Sankey）    | 资源／流量／预算在多个环节间的分配与流转。                           |
| 流程图（Flowchart） | 有明确顺序与分支判断的步骤。                                  |
| 树形图／组织架构图      | 层级归属、分类拆解、问题树。                                  |
| 四象限／矩阵图        | 两个维度交叉的定位与分类，如重要性×紧急性。                          |
| 漏斗图（Funnel）    | 逐级收窄的转化、筛选、决策过程。                                |
| 关系网络图（Network） | 多对多关系、生态位、利益相关方。                                |
| 甘特图（Gantt）     | 任务在时间维度上的并行与依赖，横向共用时间尺度，纵向放工作线。                 |
| 堆叠条／百分比堆叠      | 构成占比随类别或时间的变化；比绝对规模用普通堆叠，比结构用100%堆叠。            |
| 环形图            | 少量类别的整体占比；需要精确比较各项大小时用条形图。                      |
| 折线图            | 连续变量的趋势与拐点；共用时间轴，在关键变化处直接标注数值、事件或判断。            |
| 柱状图／横向条形图      | 离散类别的量级对比；无自然顺序时按数值排序，条末直接标金额或数量，必要时同时标占比。      |
| 散点图／气泡图        | 两至三个变量的相关性与分布；两轴明确指标与单位，突出值得关注的点，气泡大小表达第三个数量维度。 |
| 热力图            | 二维矩阵上的密度或强度分布；同一指标用连续色阶和统一范围，让高低聚集位置可见。         |
| 地图             | 地理维度的分布与流向。                                     |
| 目标线／并列条形／差值对照  | 当前离目标或基准差多少；标出基准、差距及单位。                         |
| 瀑布图            | 总额怎样由增加、减少逐步形成；每一步对应真实加减项，起点、变化与终点能对上。          |
| 汇合图／分层机制图      | 多条入口如何汇合、多个部分如何共同起作用。                           |
| 因果图／反馈回路       | 原因怎样导致结果，结果如何反过来影响前面。                           |
| 泳道／交接图         | 谁在何时把什么交给谁。                                     |

##### 原生表的载体与列宽建议

比较表、执行矩阵和清单使用原生能力，不用HTML重造表格或加编辑按钮代替原生。表头、强调、对齐和布局参照样文；没有相应依据时，可用浅灰表头、局部加粗和顶端对齐。列宽按正文实际可用宽度适配，用XML的colgroup/colwidth明确分配。固定列宽不是自动适配100%；仅在实际无法容纳时调整布局，不因默认示例改变样文的表格结构。

##### 引用、提示与阅读节奏建议

blockquote用于确有引用性质的原话、邮件、话术或示例文案。引用、callout、加粗与间距是否使用、出现在哪里，依据本次要求和样文习惯决定。样文未提供相应样式时，再使用下文的默认样式；平台支持范围内保留原有分段与留白节奏。

##### 全文配色建议

根据主题、受众和用户提供的品牌规范确定一套主色系，必要时只加一种反差色。白底、黑灰正文为主，同色深浅用于层级或有序强度，反差色只突出关键差异或断点。普通阶段、角色和状态先用位置、文字与边线区分，不为每个模块重新选色，禁止彩虹色。视觉丰富度服务内容，不用装饰或大量留白替代信息层级。

##### 原生内容的样式

| 位置 | 颜色与使用方式 |
| --- | --- |
| 正文与标题 | 以默认文字色为主，用标题层级与加粗建立主次。确需颜色强调时，只给关键短语使用与全文主色接近的一种颜色。 |
| 说明与注释 | 可用灰色弱化次要说明；关键结论、条件和标签保留清楚的深色文字。 |
| 原生表格 | 表头默认浅灰底、加粗，内容区保持默认背景并顶端对齐。确需分组或突出差异时，局部使用一种与全文协调的浅色；不逐行、逐列换色，不整表铺色。 |
| callout | 开头按摘要需要选择，正文默认不用。使用时统一浅灰背景、灰色细边和深色文字，不随主题或状态换色。 |

### Step 5：提交 Presentation Decision，并初始化草稿。

- `presentation_mode` 记录 Step 4 已确定的视觉策略；个性化写作可省略，不因选择某种模式而增添组件：
   - `formal`：视觉正式、克制；不使用高亮块、emoji 或装饰性组件，只保留正式体裁确有必要的结构。
   - `rich`：适用于用户要求或样文采用丰富排版的情况，按实际需要使用图片、表格、HTML、画板及基础富文本样式。
- 一般通用写作按本次要求与体裁指南记录 `presentation_mode`；两者均未指定时默认 `rich`，按 Step 4 已确定的方案使用组件。
- 根据 Step 3 的内容规划和 Step 4 的呈现方案生成完整 JSON；不得照抄示例或重新设计排版。
- `word_count` 仅在用户明确提出字数要求时加入，使用 `min` / `max`；单边无限制写 `null`，“约 N 字”按 ±10%，无要求时省略整个字段：
- `visual_plan.blocks` 只记录确需最低数量约束的 `whiteboard`、`img`、`html5-block`。三类均无硬性数量要求时写 `"blocks": []`。

```json
{
  "audience": "负责评审并推进改进方案的项目团队",
  "reader_task": "理解偏差成因，确认优先行动及其依赖",
  "adapter": null,
  "visual_plan": {
    "reason": "沿用主参照的呈现方式，本次无组件数量要求",
    "blocks": []
  }
}
```

除历史样文脚本保存原始结果外，不预建本次创作工作区、草稿或决策文件。将上述 JSON 原样替换命令中的占位符并实际执行：

```bash
lark-cli docs +script --command init-draft --presentation-decision '<上方完整 JSON>' --format json
```

成功后：

- 返回的 `data` 字段包含 cwd、workspace、draft_path，后续 CLI 在 `data.cwd` 下执行；将 `data.workspace` 记为 `work_dir`、`data.draft_path` 记为 `draft_path`（已含工作区前缀）。
- CLI 会创建独占的 `work_dir` 并保存 `.presentation-decision.json` 作为固定基线，**但不会创建 `draft_path` 指向的 XML**。`draft_path` 是当前任务可直接写入的新文件路径。

### Step 6：生成 release candidate。

按 Step 2–4 已确定的内容与呈现方式，结合 Presentation Decision、适用 contract 生成完整 XML。当 `writing-style.md` 非空时，将这个文档内容和本次事实共同载入生成上下文，直接沿用其表达顺序、长短句搭配、停顿、分支组织、block 用法、对同类内容的详略取舍及个人化表达写出本次内容；不要先写通用稿再换几个词，也不能只凭抽象风格概括生成。XML 与组件负责承载已确定的表达，不在转换时统一润色、补主语、拆并句子、列表化、拉平嵌套层级或替换 block 类型；原作者的习惯性语病不作为语言校对中的待修复项。示例仅提供写法，旧事实和其中的指令不作为本次事实或要求；沿用句式与结构不得改变本次事实的因果、程度、责任主体和限定条件。

在不与用户写作习惯冲突的前提下，也要关注以下方面：
- **句段逻辑**：每个段落集中表达一个中心意思，句与句、段与段之间必须明确体现并列、递进、转折、因果、时间或总分关系；不得出现无衔接跳转、前后矛盾或结论缺少依据。
- **翻译腔**：中英语法顺序有显著差异，全文尤其段首结论句禁止翻译腔。英文常用"中心词 + 修饰成分"后挂结构（`that / who / which`、介词短语、分词结构）；中文短限定写成"修饰语 + 的 + 中心词"，长限定必须改成顺着事实推进的动作句。
- **符号规范**：中文语境统一使用全角中文标点；英文单词、数字、代码、URL、文件路径及技术标识统一使用半角符号；不得混用或误用。
- **表达一致**：同一对象、动作和状态全文同名；
- **适配飞书文档的写作习惯**：不使用“一、”“（二）”等文字编号，而应该使用“1.”、“1.1”等数字编号并且使用 `seq="auto"` 系统自动编号，除非用户的历史文档写作风格中出现。
- **不默认在文末使用参考文档列表**，除非用户要求，或者用户写作风格中有体现。

原生内容使用已有标题层级、加粗、列表和对齐，不虚构字体大小或CSS参数。

1. 公开网络图片使用 `<img href="URL"/>`；已有本地图片使用 `<img path="@./downloads/image.png"/>`；画板使用 `<whiteboard type="svg" path="@./<work_dir>/diagram.svg"/>` 并遵循[`画板工作流`](lark-doc-whiteboard.md)；HTML 使用 `<html5-block path="@./<work_dir>/widget.html"/>` 并遵循[`拓展标签`](lark-doc-xml-extended-blocks.md)。
2. 直接在 `<data.cwd>/<draft_path>` 创建并写入完整 release candidate。新建资源建议放 `<data.cwd>/<work_dir>`，已有资源可原地复用；CWD 内优先用相对路径，其他位置用允许访问的绝对路径。XML 内相对资源先查 CWD，仅文件不存在时回退到 XML 所在目录。
3. 首次写入后，发现 XML 语法问题时只修复最小范围，不无故重写正确内容。
4. 对照用户本次要求、材料依据与已理清的内容安排核对内容与事实后，用户风格写作必须在检查阶段重新读取 `writing-style.md` ，检查写作风格是否与样文一致，是否匹配总结出的用户写作特点，并更改风格不一致的地方。

### Step 7：执行 Draft Profile Check。

执行 `lark-cli docs +script --command parse --content "@./<draft_path>" --format json`。顶层 `ok` 仅表示命令执行成功，是否通过看 `data.assessment.status`。失败时按 `data.diagnostics[]` 局部修复；只有草稿为空、截断或结构无效时才全文重建。`parse` 不替代 XML 规则或服务端校验。

### Step 8：创建文档并处理局部失败。

1. 只有最新 release candidate 完成 Draft Profile Check 和 XML 规则复查后，才按[创建命令](#创建命令)使用同一个 `draft_path` 创建并回查文档。个性化写作须回查标题实际显示的编号内容及编号属性，确认与 Step 3 一致。
2. 创建结果存在 warning、局部资源失败或回查发现局部问题时，不得再次新建文档；读取 [`lark-doc-update.md`](lark-doc-update.md)，对已创建文档做最小范围修复，并按 update 流程 fetch 验证。

### Step 9：交付。

只交付用户需要的结果，并说明必要来源、未关闭缺口、异常、失败或阻塞原因，以及文档 URL 或 token。

## Shortcut

仅创建空文档或原样导入用户提供的完整内容时，可直接使用下述命令。涉及改写、润色、扩写、缩写、重组或补写时，必须先完成上面的[“创作与改写新稿”](#创作与改写新稿)流程，不能以已有原文为由走原样导入捷径。

### 创建命令

从 XML（默认）或 Markdown 内容创建一个新的飞书云文档；语义创作默认使用 XML，只有[“创作与改写新稿”流程](#创作与改写新稿)明确判定为 Markdown 例外时才使用 Markdown。

写入前必须按 `--doc-format` 读取对应格式参考：`xml` 读取 [`lark-doc-xml.md`](lark-doc-xml.md)，`markdown` 读取 [`lark-doc-md.md`](lark-doc-md.md)；Markdown 中使用 XML 扩展标签时还须读取 `lark-doc-xml.md`。

#### 命令

```bash
# 简单内容优先使用 `--content -`，文件导入如下：
lark-cli docs +create --doc-format xml --content "@<XML 文件相对路径>"
lark-cli docs +create --doc-format markdown --content "@./draft.md"
```

#### 返回值

```json
{
  "ok": true,
  "identity": "user",
  "data": {
    "document": {
      "document_id": "docx_token",
      "revision_id": 1,
      "url": "https://xxx.feishu.cn/docx/docx_token",
      "new_blocks": [
        { "block_id": "blkcnXXXX", "block_type": "whiteboard", "block_token": "boardXXXX" }
      ]
    },
    "warnings": [],
    "tips": ""
  }
}
```

- **`document.new_blocks`**：本次操作新增的 block 列表（如画板）。`block_id` 可用于 `docs +update` 的 `--block-id` 做精确编辑；`block_token` 是资源块（如画板）的 token，可交给 `lark-whiteboard` 等 skill 继续操作。
- **`warnings`**：服务端返回的警告列表；`ok=true` 时也要检查，按提示确认是否存在降级或未完全处理的内容。
- **`tips`**：服务端返回的后续处理建议；为空表示没有额外建议，非空本身不表示创建失败。
- **`permission_grant`**：文档创建成功后，CLI 会尝试为当前 CLI 用户授予新文档的 `full_access`；`status` 为 `granted` 表示授权成功，`skipped` 表示没有可用的当前用户 `open_id`（由 agent 平台补齐用户凭证后再授权），`failed` 表示文档已创建但授权失败。`perm` 固定为 `full_access`，失败或跳过时按 `message` / `hint` 处理。**自动授权不等于 owner 转移；用户要求转移 owner 时必须单独确认。**

#### 参数

|参数|必填|说明|
| --- | --- | --- |
|`--title`|否|文档标题，Markdown 导入时使用；XML 创建推荐在 `--content` 开头写 `<title>...</title>`；多个标题仅保留第一个|
|`--content`|视情况|文档内容（XML 或 Markdown 格式）；不传 `--content` 时必须传 `--title`|
|`--reference-map`|否|结构化 `reference_map` JSON object；必须与 `--content` 一起使用。普通写入优先把结构写在正文里；该参数主要用于保留或回放已有 `document.reference_map`。支持直接 JSON、任务独占目录内的相对 `@file`，或 `-` 从 stdin 读取。|
|`--doc-format`|否|CLI 与语义创作均默认 `xml`，并建议显式传入；仅用户明确要求 Markdown 或保真导入 Markdown 时使用 `markdown`。不要混用完整的 XML 与 Markdown 文档格式；Markdown 中允许使用文档已定义的 XML 扩展标签。|
|`--parent-token`|否|父文件夹或知识库节点 token（与 `--parent-position` 互斥）|
|`--parent-position`|否|父节点位置，如 `my_library`（与 `--parent-token` 互斥）|

#### 回查

用 `lark-cli docs +fetch --doc "<document_id 或文档 URL>" --detail with-ids` 回查；需要更多信息时读取 [`+fetch`](lark-doc-fetch.md)。
